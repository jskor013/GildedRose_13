# Gilded Rose C++17 updateQuality() 코드 품질 분석 보고서

## 1. 작성 목적

본 보고서는 `cpp/src/GildedRose.cpp`의 `GildedRose::updateQuality()` 구현을 SOLID 원칙과 Code Smell 관점에서 분석한 작업 내용을 정리한다.

Gilded Rose의 현재 구현은 아이템 이름 문자열 기반 분기와 품질 변경 규칙이 하나의 메서드에 집중되어 있으므로, 리팩토링 전 구조적 위험과 개선 우선순위를 명확히 파악하는 것이 중요하다.

## 2. 적용 대상

- `cpp/src/GildedRose.cpp`의 `GildedRose::updateQuality()`
- 아이템 이름 기반 분기 구조
- `quality`와 `sellIn` 변경 로직
- Magic Number와 문자열 리터럴 사용 지점
- 향후 C++17 기반 리팩토링 방향

## 3. 핵심 분석 내용

### 3.1 SRP 위반

`updateQuality()`는 현재 아이템 타입 판별, 품질 증감, 판매 기한 감소, 만료 후 추가 처리, 경계값 보정을 모두 직접 수행한다.

이 구조는 하나의 메서드가 여러 변경 이유를 갖게 하므로, 신규 아이템 규칙을 추가하거나 기존 품질 정책을 조정할 때 동일한 메서드를 반복 수정하게 만든다.

### 3.2 OCP 위반

아이템 타입이 `Aged Brie`, `Backstage passes to a TAFKAL80ETC concert`, `Sulfuras, Hand of Ragnaros` 문자열 비교 조건문에 직접 결합되어 있다.

따라서 `Conjured` 같은 신규 아이템 규칙을 추가하려면 기존 `if/else` 체인을 수정해야 하며, 분기 순서 변경에 따른 회귀 위험도 커진다.

### 3.3 Magic Number와 문자열 리터럴

`0`, `50`, `11`, `6` 같은 값이 의미 있는 이름 없이 직접 사용된다.

- `0`: 일반 품질 하한
- `50`: 일반 품질 상한
- `11`: Backstage Pass 10일 이하 규칙을 `< 11`로 표현한 값
- `6`: Backstage Pass 5일 이하 규칙을 `< 6`으로 표현한 값

이 값들은 `kMinQuality`, `kMaxQuality`, `kBackstageDoubleIncreaseThreshold`, `kBackstageTripleIncreaseThreshold`처럼 도메인 상수로 분리하는 것이 적절하다.

### 3.4 주요 Code Smell

현재 구현에서 확인한 주요 스멜은 다음과 같다.

- Long Method: 모든 규칙이 `updateQuality()` 하나에 집중되어 있다.
- Duplicated Code: `quality > 0`, `quality < 50`, `Sulfuras` 예외 처리가 반복된다.
- 조건문 복잡도: 아이템 타입과 판매 기한 조건이 중첩되어 읽기 어렵다.
- Obscure Code: Backstage Pass 만료 시 `quality - quality`로 0을 만드는 표현은 의도가 직접 드러나지 않는다.
- Primitive Obsession: 도메인 타입 대신 문자열과 정수 조건에 규칙이 묶여 있다.

### 3.5 C++17 개선 방향

우선은 작은 함수 추출과 상수화를 통해 동작 변경 없이 구조를 정리하는 것이 안전하다.

이후 아이템별 갱신 규칙을 `NormalPolicy`, `AgedBriePolicy`, `BackstagePassPolicy`, `SulfurasPolicy` 같은 전략으로 분리하면 `updateQuality()`는 순회와 정책 호출만 담당할 수 있다.

Backstage Pass처럼 임계값과 증가량이 데이터로 표현되는 규칙은 테이블 기반 접근도 가능하다. 다만 기존 `Item` 구조체를 변경하지 말아야 하므로, `std::variant`는 외부 래퍼나 분류 결과에 제한적으로 적용하는 것이 적절하다.

## 4. 기대 효과

- `updateQuality()`의 책임을 줄여 리팩토링 안정성을 높인다.
- 신규 아이템 규칙 추가 시 기존 분기 수정 범위를 줄인다.
- Magic Number와 긴 문자열 리터럴로 인한 오타 및 해석 비용을 줄인다.
- 품질 경계값 보정 로직을 한곳에 모아 회귀 가능성을 낮춘다.
- C++17 기준의 점진적 리팩토링 방향을 명확히 한다.
